# 建议原审核请求保存与恢复

2026-11-04，仅源码及人工审阅。未编译、类型检查、测试、运行浏览器/接口、打开数据库或发布。

## 准备与原身份

建议详情的审核表单改为 Prepare original review。用户填写confirm/reject、理由并确认审阅来源后，客户端和服务端使用同一规范格式核对原请求。页面先读取可信submission-context；准备动作重新核对页面原网关和tenant/workspace/project/actor/client。绑定变化重建表单，不把旧内容自动带到新身份。审核能力提示不授予权限，实际既有confirm/reject接口继续要求已验证客户端、签名human声明和proposal.review/admin，并检查当前项目/建议/来源可见性、原版本和确认时的来源有效性。

每次准备前修改决定或理由分配新随机键并撤销准备确认。准备规范化理由后冻结完整原请求，进入保存/审阅/发送界面，并尝试保存浏览器副本；准备阶段只查询身份，不发送审核命令。新准备后不能在原请求界面改理由、决定、版本或键。尚未准备的输入仍仅在当前页面中；旧页面中没有留下完整副本的请求不能从新恢复页推测重建。

## 独立原请求格式

v1为 `{schema_version:1,kind:'proposal-review-submission',binding,request_key,proposal_id,expected_revision,decision,reason}`。binding沿用创建原请求的完整原网关及五字段身份格式，但文件类型和浏览器库独立；不把创建请求、编辑草稿或回执作为审核请求载入。原请求不包含登录令牌、不保存用户确认勾选，也不把文件中的身份视为当前授权。

proposal_id为ULID；expected_revision为正安全整数且加1仍安全；decision精确为confirm或reject；reason按既有proposalText检查非空、最多2000字符、不含NUL/孤立代理字符，准备时trim，恢复时必须已规范化且不补默认值。原键为1–255可见ASCII，保持既有幂等约束。顶层/绑定严格字段校验，拒绝未知或缺失字段；有限JSON完整输入及pretty文件均最多32 KiB。规范编码按对象键排序，数组顺序保留，不能靠字段顺序变化制造异文。

## 浏览器保存和目录

独立IndexedDB `planemem-proposal-review-originals` v1包含originals与directory，复用既有双槽事务工具及完整身份/原键的槽键生成器；库独立，和创建/编辑库无碰撞。槽键最多16 KiB、目录4 KiB，目录只含原键/建议ID/决定/原版本，不包含完整理由。写入在同一事务先核对已有双槽，仅缺失才add，已有完整同文保留，半槽、损坏或异文拒绝；新写完整读回后等待事务完成才确认保存。

恢复目录按当前完整绑定范围每页最多20项，按存储键顺序而非时间排序；返回前完整核对每个正文与摘要。第21项用于判断续页，不作为已完整核验记录返回。选中后按原键重新读取双槽并比较所选摘要；两槽缺失显示当前未找到，不能推断历史提交失败。读取缺库不初始化、不升级、不迁移；显式保存可初始化v1结构。分页为多次当前观察，不是跨页快照。

## 独立恢复页与文件

`/proposals/recover-review` 独立获取当前可信身份，不依赖建议列表/详情或当前仍处于proposed状态。目录选择、按原键查找、UTF-8文件或完整JSON文本均可载入；文件读前检查大小，读后检查实际字节数、严格UTF-8及完整结构，必须匹配当前绑定。载入后只展示完整原请求，不自动保存、迁移或发送，也不根据当前建议重写原版本或决定。

完整原请求可导出为proposal-review-original.json，亦可从只读文本框复制。下载只说明浏览器收到请求，需确认文件真正保存；文件包含审核理由和原身份，按内容敏感程度保管。浏览器清理、隐私模式、存储驱逐、更换浏览器配置或设备可导致本地副本丢失，需独立文件。恢复本地副本不证明曾经发送、尚未发送或已经完成；旧直接审核路径仍为兼容保留，旧标签页需刷新后使用新流程，不能凭空恢复历史缺失原请求。

## 明确发送与未知结果

每次Send or retry original review都要求重新确认完整原决定和支持来源，随后重新保存、完整读回并确认浏览器事务提交；本次保存失败或过期则本次不派发。完成保存后才调用服务端动作；服务端先比较配置网关及可信submission-context原身份，再按原键向既有 `/v1/proposals/{id}/confirm|reject` 发送原expected_revision和reason，并带原actor/client前置条件头。页面和服务端使用当前项目范围约束，账号/客户端切换不能把请求改绑。

这是写请求的显式重试：若原请求从未到达，重试可能首次记录该审核决定。它不是只读查询；独立的Check original review result按钮已接入[原审核回执查询](proposal-review-receipt-runtime.md)，不依赖保存，不发送决定。相同原键/决定/版本/理由由既有服务端幂等记录重放，不增加新审核；真实human及review权限、当前可见性仍在每次调用强制检查。不同键、不同账号、其他标签页之间没有全局未知结果锁，不能依据本地缺副本自动发起新决定。

返回成功须服务端和客户端核验完整封套：schema、trace、唯一proposal来源、原ID/期望状态/revision+1、event_id、规范UTC时间、replayed、外层revision/ETag和正安全server_cursor。服务端还核对本次HTTP trace头；原创建使用同一有界传输分支，原审核现也纳入成功64 KiB、错误16 KiB与30秒单请求期限，禁止重定向或自动重试。身份预检另有一次30秒请求限制；客户端整个保存加服务端动作的本地等待为30秒，因此客户端超时后服务端仍可能继续。

只有完整有效回执才显示已确认的历史结果，并保留原请求供导出；不自动替换页面为当前详情或清除本地记录。HTTP拒绝、身份错误、网络/读取超时、无效或不匹配回执均保持冻结原请求，不自动换键、放弃、解锁或重发。当前建议详情另开页面读取，不把历史回执等同于当前来源有效性。再次确认重试时使用同一完整原请求。

所有本地读写、文件导入及准备/发送等待受30秒操作期限约束，数据库打开/事务各10秒；操作期间锁定同一组件操作，离开组件中止本地等待并忽略迟到结果。客户端取消和超时不保证服务端审核取消，不能把未知结果解释为回滚。后续保存或导出成功也不证明审核成功；完整原请求始终保留。

本轮没有未准备审核草稿自动保存、审核原请求整批备份/清理、持久审核回执历史、旧页面缺失记录迁移或跨设备协调；新增浏览器结构仅源码，后续只读回执增量已接入Gateway/SDK/Mock/Web及CLI/MCP，无服务端schema/依赖变化。运行兼容和真实权限恢复证据留后续。
