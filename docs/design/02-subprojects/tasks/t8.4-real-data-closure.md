# T8.4 真实数据数据库闭环与运行时恢复

## 目标

把 Plane Webhook、事件、投影状态、Context Search 索引和审计写入同一条可回查的数据链路。进程重启或 Pod 滚动更新后，运行时必须从 PostgreSQL 恢复事件消费进度和搜索结果，重复投递必须返回 `duplicate`，不能再次产生投影或搜索副作用。

## 边界与依赖

| 边界 | 提供方 | 消费方 | 稳定物 |
|---|---|---|---|
| 事件存储 | `wcp_events`、`deploy/migrations/002_contracts.sql` | 运行时恢复、审计回查 | Canonical Event 字段 |
| 投影存储 | `wcp_projection_states`、`deploy/migrations/009_runtime_state.sql` | PlaneProjection、发布验证 | scope、entity_kind、external_id、plane_version |
| 搜索存储 | `wcp_context_hits`、`deploy/migrations/009_runtime_state.sql` | SearchService、MCP resources | SearchHit |
| 审计存储 | `wcp_audit_records`、`deploy/migrations/007_audit.sql` | Webhook/API 审计 | AuditRecord |
| 部署连接 | `DATABASE_URL` Secret | API Gateway | PostgreSQL URI；密钥只通过 Secret 注入 |
| Session continuity 恢复 | `wcp_sessions`、`wcp_agent_runs`、`wcp_tool_calls`、`wcp_session_checkpoints`、`wcp_session_handoffs` | Session/Continuation service | Session/Checkpoint/Handoff 状态由 PostgreSQL hydrate，CAS 拒绝静默覆盖 |

实现只依赖这些公开数据契约，不直接读取其他任务的内存对象。`PlaneProjection` 和 `SearchService` 仍是领域组件，数据库适配集中在 `apps/api-gateway/src/runtime-persistence.ts`。

## 数据模型

### `wcp_events`

使用既有事件表保存 `event_id`、类型/版本、scope、aggregate、trace、source_refs、payload 和 `occurred_at`。事件只追加；`event_id` 是重复投递的唯一键，`aggregate_type + aggregate_id + aggregate_version` 用于重放顺序。

### `wcp_projection_states`

主键为 `(tenant_id, workspace_id, project_id, entity_kind, external_id)`。字段保存 Plane authority、最新版本、观察时间、来源事件、来源引用、状态和完整业务字段。更新使用 `ON CONFLICT ... DO UPDATE`，不能覆盖不同 scope 的行。

### `wcp_context_hits`

主键为 `(tenant_id, workspace_id, project_id, id)`。字段与 `SearchHit` 一一对应，并保存 `trace_id` 和 `updated_at`。相同 scope/id 的新 revision 更新同一行，不能在重试时累加重复命中。

### `wcp_audit_records`

接受事件和重复事件都记录一次交付审计；进程内以 `delivery_id` 幂等，进程重启后数据库保留每次新的交付审计。查询使用事件的 `trace_id`，因此能把事件、投影、Context hit 和审计串起来。

## 运行时顺序

1. `start()` 在监听端口前调用 `hydrateRuntimeState`。
2. 按 aggregate 和 version 读取 `wcp_events`，重建 `PlaneProjection` 的 event ledger 与 observed state；PostgreSQL 的 BIGINT 和 JSONB 值统一转换为运行时类型，UTC 时间统一为 `Z` 结尾。
3. 读取 `wcp_context_hits`，恢复 SearchService 和 MCP resource registry。
4. Webhook 验签、JSON 解析、Canonical Event 校验和 header/event id 一致性校验全部通过后，先查询 `wcp_events` 判断已知重复。
5. 新事件应用 projection，生成对应 SearchHit，在同一 PostgreSQL transaction 中追加事件、upsert projection、upsert hit。
6. 事务成功后写入 Webhook 审计；数据库不可用时返回 HTTP 503 和 `RUNTIME_PERSISTENCE_UNAVAILABLE`，不能返回 `accepted`。
7. Context index 先生成 SearchHit，再 upsert `wcp_context_hits`；失败返回 `CONTEXT_PERSISTENCE_UNAVAILABLE`。
8. Session/AgentRun/ToolCall/Checkpoint/Handoff 写入成功后才返回成功；启动时先 hydrate，版本冲突使用 CAS 拒绝静默覆盖。
9. 重复事件不重新应用 projection、不重新插入 event/hit，并返回 200 `duplicate`；同一 Session 幂等键在重启后仍返回原 Session。

## 事务和失败语义

- 事件、投影、Context hit 必须同一事务提交；任一 SQL 失败则整体回滚。
- 事件尚未落库时禁止把请求标记为已接受。
- 启动恢复失败时进程不监听业务端口，Kubernetes/k3s readiness 不通过；已有数据库数据不能被静默忽略。
- migration 失败必须停在部署阶段；现场已有 `008_workbench_projection`，本任务使用 `009_runtime_state`，不能复用或覆盖现场 008 的迁移记录。
- 所有错误含 `trace_id`、是否可重试和可定位的错误码；不记录密码、完整 DATABASE_URL 或 webhook secret。

## 回滚

应用回滚前冻结新写入，保留 `wcp_events` 和审计；旧 runtime 不认识 009 表时仍可读取既有审计和事件，但不能宣称具备本任务的重启恢复能力。恢复新 runtime 时先确认 009 migration，再按事件顺序重放；禁止删除或重建生产数据表。
