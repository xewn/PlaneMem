# T2.2 ai-memory MemoryService Adapter

## 目标

通过 HTTP/MCP 将 ai-memory 的 capture、recall、consolidate、handoff、claim 和 restore 接入 WorkMesh。

2026-10-25 实现进展：`apps/context-service/src/memory-adapter/mcp-provider.ts` 已提供真实 Streamable HTTP/MCP provider；`MemoryServiceAdapter` 会把外部 provider 的 handoff/claim 路由到 ai-memory，InMemory provider 继续作为离线 fixture。provider 携带 `x-trace-id`、可选认证令牌、actor/client header，正文先经过 sanitizer，所有页面请求显式传递 workspace/project。`apps/api-gateway` 已将 `context.index` 的长期记忆投影和 `context.search` 的记忆召回接入同一个 provider；生产 Compose/Helm 通过 `MEMORY_PROVIDER_MODE=ai-memory-mcp`、`AI_MEMORY_URL` 和 `MEMORY_REQUIRED` 开启闭环，局域网旧配置 `AI_MEMORY_AUTH_TOKEN` 也会被兼容读取。

持久化数据必须有 migration、索引、租户/项目 scope、软删除或版本策略；不得直接写其他任务的数据库表。

## 独立测试

## 验收标准

记忆正文仍由 ai-memory 管理，WorkMesh 只保留引用和审计

额外要求：失败必须返回可诊断的 trace_id；重试不得造成重复副作用；拒绝请求不得改变任何权威数据。

## 与其他任务的协接

### 消费

- 消费者只能调用本任务在 01-contracts 或本文件 输出和接口 中声明的 API/事件；
- 通过生成 SDK 或 HTTP/MCP Contract，不引用内部类、SQL 表或文件；
- 依赖版本写入 `release-manifest.yaml`，不使用浮动版本。

### 生产

- 生产的每个事件、API、Schema、迁移和配置都必须登记在 PR；
- 下游必须能通过 Fixture、Mock 或健康端点验证输出；
- 变更需在 docs/traceability/requirements-matrix.yaml 绑定需求和测试。

### 集成顺序

本任务先在自己的分支完成独立测试，再合并到 develop；集成测试通过后才允许被
release/* 引用。接口不兼容时禁止直接合并，必须走版本化迁移。

## 发布与回滚

本任务的镜像/包/迁移/配置必须能被 P8 收集到 Release Manifest。回滚时优先关闭 Feature Flag、回退应用版本并重放未确认事件；任何数据迁移回滚必须有验证脚本。
