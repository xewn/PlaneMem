# T0.4 Canonical Event 与 AsyncAPI

## 目标

定义 CloudEvents 风格事件封套、事件类型、版本和消费者处理约束。

## 负责人和依赖

- 负责人：契约组
- 前置任务：T0.2
- 所属子方案：根据任务编号归入对应 P0-P8；子方案入口见 ../P*/README.md。

## 文件和边界

packages/events/src/envelope.ts、packages/events/schemas/*.json、docs/design/01-contracts/canonical-events.md

本任务只能修改上述责任范围。跨目录修改必须先更新协接文档和 ADR。

## 输入

前置任务的版本化输出、`docs/design/01-contracts` 契约、`packages/test-fixtures` 共享 Fixtures，以及本任务声明的运行配置和权限上下文。


## 输出和接口

CanonicalEvent<T>、EventTypeRegistry、validateEvent、EventConsumerResult

任务输出必须带版本、trace_id、source_refs、scope 和错误封套。事件输出必须遵守 `docs/design/01-contracts/canonical-events.md`。

## 数据设计

event_id、aggregate_version、correlation/causation、payload、sensitivity

持久化数据必须有 migration、索引、租户/项目 scope、软删除或版本策略；不得直接写其他任务的数据库表。

## 实现步骤

1. 读取并确认前置任务的契约和 Fixtures；
2. 先为正常路径、权限拒绝、重复、超时和版本冲突编写失败测试；
3. 实现最小接口和运行时校验；
4. 接入 trace、audit、idempotency 和 health/readiness；
5. 在独立环境运行本任务测试；
6. 更新 OpenAPI/AsyncAPI/JSON Schema、Fixture、追踪矩阵和运行文档；
7. 生成可供下游消费的版本化 artifact。

## 独立测试

缺字段、错误版本、重复 event_id、聚合版本跳变、payload schema

测试必须不依赖未完成的下游任务；需要外部能力时使用 packages/test-fixtures 或明确版本的 Compose 服务。

## 验收标准

P1/P3/P6/P8 使用同一事件封套

额外要求：失败必须返回可诊断的 	race_id；重试不得造成重复副作用；拒绝请求不得改变任何权威数据。

## 与其他任务的协接

### 消费

- 消费者只能调用本任务在 01-contracts 或本文件 输出和接口 中声明的 API/事件；
- 通过生成 SDK 或 HTTP/MCP Contract，不引用内部类、SQL 表或文件；
- 依赖版本写入 
elease-manifest.yaml，不使用浮动版本。

### 生产

- 生产的每个事件、API、Schema、迁移和配置都必须登记在 PR；
- 下游必须能通过 Fixture、Mock 或健康端点验证输出；
- 变更需在 docs/traceability/requirements-matrix.yaml 绑定需求和测试。

### 集成顺序

本任务先在自己的分支完成独立测试，再合并到 develop；集成测试通过后才允许被 
elease/* 引用。接口不兼容时禁止直接合并，必须走版本化迁移。

## 发布与回滚

本任务的镜像/包/迁移/配置必须能被 P8 收集到 Release Manifest。回滚时优先关闭 Feature Flag、回退应用版本并重放未确认事件；任何数据迁移回滚必须有验证脚本。
