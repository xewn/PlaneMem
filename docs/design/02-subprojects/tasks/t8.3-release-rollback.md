# T8.3 Release Manifest、备份恢复与回滚

## 目标

把 Plane、ai-memory、WorkMesh、Schema、迁移、Feature Flags 固定成可恢复发布单元。

## 负责人和依赖

- 负责人：发布测试组
- 前置任务：T8.1、T8.2、T6.2
- 所属子方案：根据任务编号归入对应 P0-P8；子方案入口见 ../P*/README.md。

## 文件和边界

deploy/release-manifest.yaml、docs/runbooks/*、scripts/backup/*、scripts/rollback/*

本任务只能修改上述责任范围。跨目录修改必须先更新协接文档和 ADR。

## 输入

前置任务的版本化输出、`docs/design/01-contracts` 契约、`packages/test-fixtures` 共享 Fixtures，以及本任务声明的运行配置和权限上下文。


## 输出和接口

preflight、backup、restore、migrate、rollback、smoke

当前落地：`packages/release` 导出 `ReleaseManifest`、`preflightRelease`、`BackupBundle`、
`createBackup/restoreBackup` 和 `RollbackPlan`。preflight 检查审批与 digest；备份逐文件 hash
校验；回滚无审批不产生执行步骤，获批后固定冻结写入、恢复、上一 manifest、重放 outbox、smoke、
解冻顺序。`tools/release-manifest-cli.mjs`、`tools/sbom-cli.mjs`、`tools/run-image-vulnerability-scan.mjs` 和 `tools/rc-readiness.mjs` 生成并汇总 RC 输入，
`deploy/release-manifest.yaml` 和 `docs/runbooks/release.md` 是发布运维入口。

任务输出必须带版本、trace_id、source_refs、scope 和错误封套。事件输出必须遵守 `docs/design/01-contracts/canonical-events.md`。

## 数据设计

image digests、migration id、ai-memory version、backup metadata、flag state

持久化数据必须有 migration、索引、租户/项目 scope、软删除或版本策略；不得直接写其他任务的数据库表。

## 实现步骤

1. 读取并确认前置任务的契约和 Fixtures；
2. 先为正常路径、权限拒绝、重复、超时和版本冲突编写失败测试；
3. 实现最小接口和运行时校验；
4. 接入 trace、audit、idempotency 和 health/readiness；
5. 在独立环境运行本任务测试；
6. 更新 OpenAPI/AsyncAPI/JSON Schema、Fixture、追踪矩阵和运行文档；
7. 生成可供下游消费的版本化 artifact。

## 独立测试

backup/restore、upgrade/rollback、schema compatibility、audit/context resume

测试必须不依赖未完成的下游任务；需要外部能力时使用 packages/test-fixtures 或明确版本的 Compose 服务。

自动化入口：`P8-R01/T8.3`、`P8-R02/T8.3`、`pnpm run test:vulnerability` 和 P8 contract；Compose live 已覆盖 PostgreSQL、
SQLite、ai-memory 和对象存储恢复；历史镜像扫描结果仅作 informational 记录，RC 节点恢复和生产 smoke 仍需 RC 环境。

本轮使用传输 runtime 镜像的 Compose live 实测：`artifacts/command-reports/release-transport-sqlite/release-transport-sqlite-release.json`；SQLite 独立关闭重开证据在 `artifacts/command-reports/sqlite-live-final/`，此前安全修复路径证据保留在 `artifacts/command-reports/live-restore-security-fixed-path/`。
`compose.health`、PostgreSQL 备份/恢复（122 张 public 表前后计数一致）、ai-memory 备份/恢复抽取、
对象存储备份/恢复抽取和临时库清理均为 `passed`，并记录三类归档 SHA-256。报告在 Compose 恢复范围内为 `passed`，
SQLite 2 行关闭重开恢复也已 `passed`；生产 Smoke、RC 节点和恢复后业务校验仍待完成；本机 Helm v3.9.0 和目标 k3s Helm 门禁已通过。

## 验收标准

RC 和生产失败可回到上一可用版本且不丢事件/记忆/审计

额外要求：失败必须返回可诊断的 trace_id；重试不得造成重复副作用；拒绝请求不得改变任何权威数据。

## 与其他任务的协接

### 消费

- 消费者只能调用本任务在 01-contracts 或本文件 输出和接口 中声明的 API/事件；
- 通过生成 SDK 或 HTTP/MCP Contract，不引用内部类、SQL 表或文件；
- 依赖版本写入 `release-manifest.yaml`，不使用浮动版本。

### 生产

- 生产的每个事件、API、Schema、迁移和配置都必须登记在 PR；
- 下游必须能通过 Fixture、Mock 或健康端点验证输出；
- 变更需在 docs/traceability/requirements-matrix.yaml 绑定需求和测试。

### 集成顺序

本任务先在自己的分支完成独立测试，再合并到 develop；集成测试通过后才允许被
release/* 引用。接口不兼容时禁止直接合并，必须走版本化迁移。

## 发布与回滚

本任务的镜像/包/迁移/配置必须能被 P8 收集到 Release Manifest。回滚时优先关闭 Feature Flag、回退应用版本并重放未确认事件；任何数据迁移回滚必须有验证脚本。
